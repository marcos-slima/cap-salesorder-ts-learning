**Namespace:** `com.my.sales`

**HANA target:** SAP HANA Cloud  
**BTP services:** XSUAA, Event Mesh, Connectivity, Destination

## 1. Domain-Driven Design Mapping

### Bounded Context boundary

The **Sales bounded context** owns the complete lifecycle of a Sales Order — from
creation through delivery confirmation and billing status update. It does NOT own
product master data, business partner master, or organisational structure. Those
belong to supporting sub-domains and are referenced (not replicated) in production.

```
┌───────────────────────────────────────────────────────────┐
│  Sales Bounded Context (this CAP application)             │
│                                                           │
│  Aggregate: SalesOrders ───────────────────────────────┐  │
│    Root:    SalesOrders (VBAK)  ← cuid + managed       │  │
│    Children (Composition — owned lifecycle):           │  │
│      SalesOrderItems (VBAP)     ← cuid + managed       │  │
│        SalesOrderItemConditions (KONV)  ← managed      │  │
│        SalesOrderScheduleLines  (VBEP)  ← managed      │  │
│        SalesOrderItemTexts              ← managed      │  │
│      SalesOrderPartners (VBPA)          ← managed      │  │
│      SalesOrderHeaderTexts              ← managed      │  │
│                                                        │  │
│  External references (Association — independent):  ────┘  │
│    Products            → Product sub-domain               │
│    BusinessPartners    → Partner sub-domain               │
│    SalesAreas          → OrgStructure sub-domain          │
└───────────────────────────────────────────────────────────┘
```

> **Note on `cuid` placement:** Both `SalesOrders` and `SalesOrderItems` carry
> `cuid` — giving each its own UUID primary key. This is required (see ADR-07)
> because grandchild entities reference `SalesOrderItems` by UUID, not by the
> business key pair `(order, itemNumber)`.

### Aggregate Root invariants

| # | Invariant | Enforced by |
|---|-----------|-------------|
| 1 | `netAmount` on header = Σ item `netAmount` | CAP after-WRITE handler |
| 2 | `submitOrder` requires ≥1 schedule line per item | CAP action handler |
| 3 | `overallStatus`, `deliveryStatus`, `billingStatus` are computed — never patched directly | `@readonly` + `@Core.Computed` |
| 4 | Logically deleted orders reject all WRITE operations | CAP before-WRITE handler |
| 5 | `soldToParty` must exist and must not be blocked | Validation in `submitOrder` |

### CAP vs RAP: aggregate enforcement

Unlike SAP RAP — where the Aggregate Root is a **first-class platform construct**
enforced by the framework (lock master / dependent, ETag cascade, BO activation
checks) — CAP does **not** enforce the aggregate pattern automatically.

| Concern | RAP | CAP |
|---------|-----|-----|
| Aggregate declaration | `define behavior` BO keyword | Convention only — no keyword |
| Lock propagation | `lock dependent by _Root` — automatic | Manual handler required |
| Child access without root | Rejected at BO activation | Silently allowed — developer discipline |
| Draft for entire tree | Generated by framework | Only if `@odata.draft.enabled` on root + correct Composition chain |
| Validation order | Framework-controlled (root first) | Developer-controlled in handlers |
| Compiler enforcement | ADT rejects violations | CDS compiler accepts violations; errors appear at runtime |

**Consequence:** in CAP, the aggregate boundary is enforced by architectural
discipline — correct use of `Composition`, `@restrict`, `@cds.redirection.target`,
and service topology rules documented in this file. The compiler does not
substitute for architectural review.

## 3. Key Modelling Decisions (ADRs)

### ADR-01: UUID surrogate key + business key separation

**Decision:** Every entity uses `cuid` (UUID surrogate key) as the physical
primary key. Business keys (VBELN, MATNR, etc.) are separate fields annotated
`@mandatory` with `@assert.unique`.

**Rationale:**
- Associations between entities are UUID-stable. If a VBELN is corrected, no
  child FK breaks.
- OData deep insert (`POST /SalesOrders` with embedded items) works correctly
  because CAP generates UUIDs for all levels.
- Aligns with SAP BTP best practices for cloud-native persistence.

**Consequence:** Service consumers who know only the VBELN must first query
`?$filter=salesOrder eq 'XXXXXXX'` to resolve the UUID before navigating to
children.

---

### ADR-02: SalesOrderPartners composition (VBPA pattern)

**Decision:** Partner functions (sold-to, ship-to, bill-to, payer) are stored in
a `SalesOrderPartners` composition table, not as three separate FK columns on
the header.

**Rationale:**
- Adding a new partner role requires NO schema migration.
- The SAP VBPA table uses the same pattern — this CDS model mirrors it.
- Convenience filtered associations (`soldTo`, `shipTo`, `billTo`) on the root
  provide direct navigation without breaking the flexible design.

**Trade-off:** Queries that only need the sold-to name navigate through the
partners table. Mitigated by `SalesOrderItemsFlat`, which denormalises
`soldTo.partnerName` alongside `salesOrgCode` and `distributionChannelCode`.

---

### ADR-03: Three-service architecture

**Decision:** Three separate OData services instead of one monolithic service.

| Service | Path | Purpose |
|---------|------|---------|
| `SalesOrderService` | `/api/orders` | Transactional CRUD + domain actions |
| `SalesCatalogService` | `/api/catalog` | Read-only master / reference data |
| `SalesAnalyticsService` | `/api/analytics` | Analytical queries — SAC, Datasphere, AI |

**Rationale:**
- Different security requirements: analytics readers must not see draft orders;
  catalog readers must not see order details.
- Different caching strategies: catalog data is mostly static; order data is volatile.
- Different `$metadata` documents: Fiori apps only download metadata for their
  service, reducing client startup time.
- `@Analytics.query` annotations required by SAC would pollute the transactional
  service `$metadata`.
- Flat item views (`SalesOrderItemsFlat`, `ScheduleLinesFlat`) **must not** be in
  the same service as the transactional `SalesOrderItems` entity set — see ADR-09.

---

### ADR-04: `@odata.draft.enabled` on SalesOrders (root only)

**Decision:** Enable CAP Draft on `SalesOrders` only. Do NOT annotate child
entity sets (`SalesOrderItems`, `SalesOrderScheduleLines`, etc.).

**Rationale:**
- Fiori Flexible Column Layout Object Pages require Draft to function correctly.
- Users entering a complex multi-item order should be able to save progress
  without committing.
- CAP Draft generates `DraftAdminData` and shadow tables automatically for the
  entire Composition tree — no annotation on children needed or allowed.

**Consequence:**
- The OData `$metadata` gains `IsActiveEntity`, `HasDraftEntity`, `HasActiveEntity`
  navigation properties on `SalesOrders` and all its Composition children.
- Integration Suite iFlows must append `?$filter=IsActiveEntity eq true` in all
  read queries to avoid returning draft rows.
- Annotating a Composition child with `@odata.draft.enabled` would create duplicate
  draft tables and conflicting OData navigation properties — this is a
  compiler-accepted but runtime-breaking mistake.

---

### ADR-05: `StatusTracked` aspect — computed-only status fields

**Decision:** `overallStatus`, `deliveryStatus`, `billingStatus` are declared
`@readonly @Core.Computed` and populated exclusively by CAP handlers, never by
external PATCH requests.

**Rationale:**
- Status fields are aggregate invariants. Allowing external PATCH breaks business
  rules and bypasses domain event emission.
- `@Core.Computed` signals to Fiori Elements that the field is server-calculated;
  the form renders it as a display field, not an editable input.
- Status transitions trigger domain events published to Event Mesh.

---

### ADR-06: `EventEmitting` aspect + CAP Outbox

**Decision:** Domain events are published via the CAP Outbox pattern, not inline
in the handler.

**How it works:**
1. Handler calls `cds.emit('salesorder.submitted', payload)` inside the transaction.
2. CAP Outbox writes the event to an `OutboxMessages` table in the **same HANA
   transaction** — atomicity guaranteed.
3. A background job reads `OutboxMessages` and publishes to SAP Event Mesh.
4. If Event Mesh is unavailable, events accumulate in Outbox and are retried —
   no lost events.

**`excluding` and EventEmitting fields:**  
`lastEventType` and `lastEventAt` are excluded from the OData service contract
via `excluding { … }` on the service projection. This hides them from OData
consumers but does **not** prevent CAP handlers from writing them via
`cds.update()` after commit. The `excluding` keyword is a contract filter, not a
write guard.

**Event types published:**
```
com.my.sales.salesorder.created.v1
com.my.sales.salesorder.submitted.v1
com.my.sales.salesorder.delivered.v1
com.my.sales.salesorder.deleted.v1
com.my.sales.salesorder.item.added.v1
```

### ADR-07: `cuid` on SalesOrderItems — the composite FK cascade problem

**Decision:** `SalesOrderItems` carries its own `cuid` UUID key in addition to
the business pair `(order, itemNumber)`. Grandchild entities
(`SalesOrderItemConditions`, `SalesOrderScheduleLines`, `SalesOrderItemTexts`)
reference `SalesOrderItems` via a **simple UUID FK**, not via a structured FK.

**Problem this solves — the composite FK cascade:**  
When a grandchild entity references a parent via a structured FK
`{ order, itemNumber }`, the CAP compiler must redirect that association through
every projection of the parent — including flat read views. Flat views omit
navigation fields by design (e.g. `order` is renamed to `salesOrderNumber` in
`SalesOrderItemsFlat`). The redirect fails:

```
[ERROR] Can't redirect association "item" — target does not project element "order"
```

Replacing the composite FK with a single UUID FK eliminates the problem: the
grandchild has one column (`item_ID UUID`) and the compiler redirects it through
any projection that exposes `ID`.

**Corollary — flat views must project `ID`:**  
Even with a simple UUID FK, the flat view `SalesOrderItemsFlat` must explicitly
project `ID` in its field list. Without it, the compiler raises:

```
[ERROR] Can't redirect association "item" — target does not project element "ID"
```

`ID` was added to `SalesOrderItemsFlat` for this reason.

**Schema impact:**

| Entity | PK columns in HANA |
|--------|--------------------|
| `SalesOrders` | `ID UUID` (from `cuid`) |
| `SalesOrderItems` | `ID UUID` (from `cuid`) |
| `SalesOrderItemConditions` | `item_ID UUID` + `conditionStep INTEGER` |
| `SalesOrderScheduleLines` | `item_ID UUID` + `scheduleLineNo INTEGER` |
| `SalesOrderItemTexts` | `item_ID UUID` + `textId NVARCHAR(4)` |

### ADR-08: `@cds.redirection.target` — resolving association ambiguity

**Decision:** The `SalesOrders` projection in `SalesOrderService` is annotated
`@cds.redirection.target: true`.

**Problem this solves:**  
`SalesOrderService` exposes two entity sets that both trace back to the domain
entity `com.my.sales.SalesOrders`:

- `SalesOrders` — direct projection of `sales.SalesOrders`
- `OpenOrders` — projection of `sales.OpenOrdersView`, which is a view of
  `sales.ActiveSalesOrders`, which is itself a filtered view of `sales.SalesOrders`

The CAP compiler traces the view chain to the base entity and finds two
candidates for redirecting the association `SalesOrderItems.order`. It cannot
auto-select and raises:

```
[ERROR] Add "@cds.redirection.target" to either "SalesOrderService.OpenOrders"
or "SalesOrderService.SalesOrders" — can't auto-redirect
"SalesOrderService.SalesOrderItems:order" otherwise
```

**Why `SalesOrders`, not `OpenOrders`:**  
`OpenOrders` is a filtered read-only view (only non-deleted, non-delivered orders).
It omits status fields and `deletionIndicator`. It cannot serve as the canonical
redirect target for a transactional association because write operations navigating
through it would silently fail for delivered or deleted orders.

**Rule:** always place `@cds.redirection.target: true` on the **fullest, writable
projection** of the domain entity in the service — never on a filtered or
read-only view.

**When this pattern always appears:**  
Any service that exposes both a transactional entity and one or more views derived
from that same entity (open orders view, history view, summary view, etc.) will
trigger this error. Apply `@cds.redirection.target: true` proactively when
designing the service, not reactively after the compiler error.

### ADR-09: Flat views and transactional entity sets must not coexist in the same service

**Decision:** `SalesOrderItemsFlat` and `ScheduleLinesFlat` are exposed only in
`SalesAnalyticsService`. They are **not** exposed in `SalesOrderService`, which
also exposes the transactional `SalesOrderItems` entity set.

**Problem this solves:**  
When a service exposes two entity sets that both resolve to the same domain entity
— one as a full projection (`SalesOrderItems`) and one as a flat view
(`SalesOrderItemsFlat`) — the CAP compiler picks the **last one encountered during
compilation** as the redirect target for Composition back-references. The flat view
is missing the `order` field (renamed to `salesOrderNumber`), breaking the `ON`
condition of the `items` Composition:

```
[ERROR] Target "SalesOrderService.ItemsFlat" of "items" is missing element "order";
use 'redirected to' with an explicit ON-condition
```

**Why `@cds.redirection.target` is not the solution here:**  
Adding the annotation on `SalesOrderItems` would resolve the redirect conflict, but
it would not address the design problem: two fundamentally different representations
of the same entity coexisting in the same service contract. The flat view exists for
read-only reporting; the transactional entity exists for CRUD. Mixing them in the
same `$metadata` document creates consumer confusion and makes `$apply` aggregation
semantics ambiguous.

**Rule:** expose flat/denormalised views derived from a Composition child only in a
service that does **not** also expose that child as a transactional entity set. The
header-level `OpenOrders` view is an exception — it derives from `SalesOrders` (the
root), not from `SalesOrderItems`, so it does not compete with the `items`
Composition redirect.

### ADR-10: `authenticated-user` must not appear alongside explicit roles in `@requires`

**Decision:** `SalesCatalogService` uses explicit roles only in `@requires`.
`authenticated-user` was removed.

**Problem this solves:**  
`authenticated-user` is the least-privileged catch-all in the CAP security model.
Once present in a `@requires` list, **any** user holding a valid XSUAA token gains
access to all entity sets in the service — the explicit roles become unreachable
conditions.

```cds
// WRONG — authenticated-user makes the other roles irrelevant
@requires: ['CatalogReader', 'SalesProcessor', 'authenticated-user']

// CORRECT — every caller must hold at least one of the listed roles
@requires: ['CatalogReader', 'SalesProcessor', 'SalesManager', 'SalesAuditor']
```

**Operational consequence:** assign `CatalogReader` to every BTP Role Collection
that needs catalog access (including collections that also hold `SalesProcessor` or
`SalesManager`). This keeps the access model explicit and auditable in the BTP Cockpit.

### ADR-11: `@Analytics.Dimension` and `@Analytics.Measure` are mandatory on `@Analytics.query` entities

**Decision:** Every field of every `@Analytics.query` entity set in
`SalesAnalyticsService` is explicitly annotated as either `@Analytics.Dimension: true`
or `@Analytics.Measure: true` with `@Aggregation.default`.

**Rationale:**  
Without these annotations, SAC and Datasphere treat **all** fields as dimensions.
The `$apply=aggregate(netAmount with sum)` operation returns incorrect results or
fails with a type error. The annotations are not optional decorations — they are the
OData Analytics protocol contract between CAP and SAC.

**Pattern:**
```cds
@Analytics.query: true
entity MyQuery as projection on domain.MyView {
    @Analytics.Dimension: true   customerCode,
    @Analytics.Dimension: true   orderDate,
    @Analytics.Dimension: true   currency,
    @Analytics.Measure  : true
    @Aggregation.default: #SUM   netAmount
};
```

### ADR-12: `using` aliases must be distinct across files in the same service

**Decision:** The two `using` statements in `services.cds` use distinct aliases:
`sales` (for `db/domain/sales-orders`) and `catalog` (for `db/masterdata/master-data`).

**Problem this solves:**  
Both files share the namespace `com.my.sales`. If both `using` statements used the
alias `domain`, the second declaration would silently overwrite the first in the CDS
compiler's symbol table. All references to `domain.SalesOrders` would resolve to the
master-data file at runtime, producing opaque "entity not found" errors.

```cds
// WRONG — second alias silently shadows the first
using { com.my.sales as domain } from '../db/domain/sales-orders';
using { com.my.sales as domain } from '../db/masterdata/master-data';

// CORRECT — distinct aliases make each source explicit
using { com.my.sales as sales }   from '../db/domain/sales-orders';
using { com.my.sales as catalog } from '../db/masterdata/master-data';
```

## 6. Consumer Scenarios

### Fiori / SAPUI5
- App connects to `SalesOrderService` (`/api/orders`)
- Uses `@odata.draft.enabled` Object Page for create/edit (Draft inherited by all Composition children automatically)
- List Report binds to `OpenOrders` entity set for the header overview
- Item-level list reports bind to `SalesAnalyticsService/ItemsFlat`
- F4 value helps bind to `SalesCatalogService` (`/api/catalog`)
- Status badges use `DeliveryStatus` enum metadata (OData EnumType)
- **Bootstrap requirement:** each `index.html` must have a `<div data-sap-ui-component data-name="<ns>.Component">` in the body; `sap/ui/core/ComponentSupport` scans the DOM for this element — without it the page renders blank with no error

### SAP Build Apps
- Connects to `SalesCatalogService` for product/partner browsing
- Connects to `SalesOrderService` for order placement
- No custom Fiori Elements needed — Build Apps uses OData natively

### SAP Joule Skills / AI Agents
- Reads `SalesAnalyticsService` for conversational analytics:  
  *"How many open orders does customer Acme have this month?"*
- Reads `SalesCatalogService` for entity resolution:  
  *"What's the product code for the 15-inch laptop?"*
- Calls `SalesOrderService.submitOrder` action via function calling
- Flat, self-describing entity sets (`OpenOrdersQuery`, `ItemRevenueQuery`,
  `DeliveryScheduleQuery`) reduce the number of navigation hops an AI agent
  needs to answer a question

### External APIs / SAP Partner integration
- OAuth2 client credentials flow → XSUAA → BTP service binding
- Scopes: `SalesProcessor` for order submission, `CatalogReader` for lookups
- All endpoints versioned via the `/api/` path prefix; `/api/v2/` is achievable
  by adding a new service definition without modifying the domain model
- Inbound integrations must use `IsActiveEntity eq true` in all read queries

## 7. CDS Compiler Rules — Redirection Reference

This section summarises the association redirect rules discovered during
development. Each rule has a deterministic trigger and a known fix.

| # | Error message (abbreviated) | Trigger | Fix |
|---|----------------------------|---------|-----|
| R1 | `does not project element 'order'` | Grandchild has structured FK `{ order, itemNumber }`; flat view omits `order` | Give parent entity its own `cuid`; grandchild uses simple UUID FK |
| R2 | `does not project element 'ID'` | Parent has `cuid` but flat view does not project `ID` | Add `ID` to the flat view's field list |
| R3 | `Target 'X' of 'Y' is missing element 'order'` | Transactional entity and flat view of same entity coexist in one service; compiler picks flat view as redirect target | Move flat views to a separate service that does not expose the transactional entity |
| R4 | `can't auto-redirect — add @cds.redirection.target` | Service has two entity sets tracing to the same domain entity (e.g. `SalesOrders` + `OpenOrders`) | Add `@cds.redirection.target: true` to the fullest, writable projection |

## 8. Annotation Cheat Sheet

| Annotation | Where used | Effect |
|-----------|------------|--------|
| `@assert.unique` | Entity | HANA unique index on specified fields |
| `@assert.range` | Enum type | CAP validates value is a declared member |
| `@mandatory` | Field | OData `Nullable=false`; Fiori marks field required |
| `@readonly` | Field / Entity | OData field is not writable; Fiori renders as display |
| `@Core.Computed` | Field | Fiori Elements hides from editable forms |
| `@UI.Hidden` | Field | Field excluded from auto-generated Fiori UI |
| `@Measures.ISOCurrency` | Amount field | OData measure + unit pair; Fiori renders currency symbol |
| `@Measures.Unit` | Qty field | OData measure + unit pair; Fiori renders UoM |
| `@cds.autoexpose` | Entity | CAP auto-exposes in any service that projects from it |
| `@odata.draft.enabled` | Root entity only | CAP Draft; Fiori Object Page create/edit; do not repeat on children |
| `@Analytics.query` | Entity / View | SAC live connection + `$apply` aggregation support |
| `@Analytics.Dimension` | Field in analytics entity | Groupable / filterable attribute for SAC |
| `@Analytics.Measure` | Field in analytics entity | Aggregatable numeric field for SAC |
| `@Aggregation.default` | Measure field | Default aggregation function (`#SUM`, `#MIN`, `#MAX`, `#AVG`) |
| `@restrict` | Entity in service | Fine-grained CRUD permission per role |
| `@requires` | Service | Service-level role guard; never mix with `authenticated-user` |
| `@cds.redirection.target` | Entity in service | Explicit redirect target when multiple candidates exist for same domain entity |
| `localized` | String field | CAP generates `_texts` table; auto language resolution at runtime |

## 9. Deployment: Single-Tenant Validation Variant

The reference `mta.yaml` in this project is designed as a full
multi-tenant SaaS blueprint — MTX sidecar, Service Manager (HDI per
tenant), Event Mesh, Connectivity service, `tenant-mode: shared`.
That is correct for the reference architecture this project
demonstrates, but it is disproportionate machinery just to validate
that the domain model and services work against real HANA Cloud +
XSUAA.

A stripped single-tenant variant was used for that validation —
same domain model, same CDS service definitions, no code changes to
`db/` or `srv/*.cds`, only a reduced `mta.yaml`:

- Modules: `cap-salesorder-ts-srv` + `cap-salesorder-ts-db-deployer`
  only (no MTX sidecar).
- Resources: `cap-salesorder-db` (HANA) + `cap-salesorder-auth`
  (XSUAA) only (no Event Mesh, Connectivity, Service Manager).
- `tenant-mode: dedicated` instead of `shared` — the standalone
  `xs-security.json` in this repo already defaults to `dedicated`,
  which is what a single-tenant variant needs; the multi-tenant
  `mta.yaml` overrides this to `shared` in its inline `config:` block.

### Bugs found only when deploying against real HANA (not `cds watch`)

None of these surface locally against SQLite — they only appear on a
real Cloud Foundry + HANA Cloud deploy:

1. **`oauth2-configuration` fields must be camelCase**
   (`tokenValidity`, `refreshTokenValidity`), not kebab-case
   (`token-validity`, `refresh-validity`) — kebab-case is only valid
   in `mta.yaml` module/build keys, not inside the XSUAA broker's own
   config schema. Wrong case fails service creation with
   `Unrecognized field`.
2. **`@cap-js/hana` is not a transitive dependency** of `@sap/cds` —
   it must be an explicit `dependencies` entry (not `devDependencies`)
   for the production/HANA profile. Without it: `Cannot find module
   '@cap-js/hana'` at boot.
3. **Seed data can violate `String(N)` length against HANA even when
   SQLite accepted it silently** — SQLite is lenient about string
   length, HANA enforces it strictly. One seed CSV had `HALBF` (5
   chars) where the CDS model declares `String(4)` (matching the real
   SAP MTART code `HALB`) — fixed the data, not the type.
4. **`httpx`-style form encoding of OData `$filter` breaks against
   the CAP OData v4 parser**: a query param encoded with `+` for
   spaces (form-urlencoded convention) is rejected — the parser
   expects strict RFC 3986 `%20`. Affects any external client library
   that defaults to form encoding for query params, not specific to
   this project's client code.

### `client_credentials` scope grant — simpler than it first looks

For a machine-to-machine client (no interactive user) to receive a
scope in its token, **Role Collections do not apply** — those are for
interactive login (Authorization Code Grant) only. The mechanism for
`client_credentials` is the `authorities` array in `xs-security.json`:

```json
"authorities": ["$XSAPPNAME.CatalogReader"]
```

Added directly to the app's own `xs-security.json` (no separate
consumer XSUAA instance needed for a same-instance grant), redeployed,
then a fresh service key generated. Verified: token response `scope`
field included `<xsappname>.CatalogReader` alongside `uaa.resource`.

### HANA Cloud Free Tier: automatic daily stop

The Free Tier HANA instance **stops automatically every day at 1PM
local time** — not a fault, documented platform behavior. Any deploy
or test attempted while stopped fails with `HANA Database instance is
stopped` (service creation) or `Pool resource could not be acquired
within 1s` (already-running app trying to query). Resume manually via
**HANA Cloud Central → instance → Resume** before testing; takes a
few minutes to reach `Running`.

### Event Mesh: Solace Cloud direct connection (SDK-free alternative)

SAP's own standalone Event Mesh service has been phased out for new
BTPEA-contract customers (existing CPEA customers can still license
it per SAP's own March 2026 community response — the deprecation is
contract-model-specific, not universal), replaced by a choice between
Advanced Event Mesh (AEM, licensed separately) or EMIS (Event Mesh
embedded in Integration Suite, no extra license cost but requires a
paid Integration Suite Standard/Premium subscription — not available
on Trial). Neither path is free within a BTP Trial account.

**Alternative used here**: AEM is Solace-powered under the hood, and
Solace Cloud offers a genuinely free "Developer" tier broker
(`console.solace.cloud`, no credit card), connected to directly via
AMQP 1.0 — completely independent of any SAP-provisioned service or
BTP entitlement.

**Library choice**: `amqp10` (shown in Solace's own "Get Started"
code samples) has not been published in 8 years and is unmaintained.
Used `rhea` instead — the actively maintained AMQP 1.0 client
(Apache-licensed, 86+ dependent projects, latest release within
months at time of writing).

**Two validation layers, not one**:

1. `scripts/test-solace-connection.js` — raw AMQP 1.0 connectivity
   smoke test via `rhea` directly (connect, open sender, publish).
   Proves the broker is reachable and credentials are valid. Does
   NOT exercise any CAP framework code.
2. `srv/lib/solace-messaging-service.js` — a custom
   `cds.MessagingService` subclass wired into the actual CAP Outbox
   pattern. `scripts/test-solace-cds-integration.js` validates a full
   round trip through the standard CAP API (`messaging.emit(event,
   data)` → published via `rhea` to the real Solace broker →
   received back via an AMQP receiver → dispatched to an app-level
   `.on(event, handler)` — the same mechanism `cds.emit()` inside a
   domain service handler would use in production.

**Honesty note on the `MessagingService` subclass**: the exact
internal contract for custom `cds.MessagingService` subclasses (how
`init()`, `on()`, and the outbox dispatch interact) does not have
solid, confirmed public documentation — this implementation was
written from inferred patterns (official plugins like
`@cap-js/event-broker`) and validated by running the round-trip test
above, which passed on the first attempt. Not yet wired into any real
domain event handler (`submitOrder`, `confirmDelivery`, etc.) or
tested under the actual CAP Outbox's persistent/transactional
guarantees (same-HANA-transaction write before async dispatch) — only
the direct `messaging.emit()` call path is validated so far.
